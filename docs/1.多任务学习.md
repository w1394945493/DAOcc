3. (11.16) 将实例特征注入占据BEV特征中：

- **候选框筛选：**检测头预测 3D 框，经过置信度过滤、NMS 和几何有效性检查，保留候选来源索引。
- **实例特征提取：**按来源索引，从 CenterHead.shared_conv 输出中提取对应位置的 64 维特征，暂不做 ROI 池化。
- **空间关联：**将 ego 占据网格查询点转换到增强后的 LiDAR 系，判断其是否位于预测框的 XY 投影内，建立实例到占据 BEV 单元的连接。
- **信息融合：**结合实例内容、类别和几何编码生成消息，按置信度加权聚合，通过门控残差注入占据 BEV。
- **占据预测：**融合位置在 CrossCoordinateSample 之后、final_conv 之前，随后沿原占据头输出预测。
- **训练与推理：**共用预测框建边流程，支持多 BS；筛选与建边无梯度，特征融合保留梯度。空关联保持原特征，并保留零梯度路径以兼容 DDP。
通过新增子类和模块实现，原模型主体代码保持不变。

总结：
在原 DAOcc 基线上，新增检测引导的实例级占据特征融合模块：筛选预测 3D 框，从检测 BEV 的候选来源位置提取实例特征，通过坐标对齐建立框与占据 BEV 单元的空间关联；结合类别和几何信息生成实例消息，按置信度加权聚合，并通过门控残差注入占据分支，再由原占据头完成预测。训练与推理均使用预测框建立关联，无需 GT 参与。

与StreamOcc流程对比：
- 两者都利用预测 3D 框建立实例与占据空间的联系，但 StreamOcc 将已有的实例 query 特征关联到三维体素，当前方案从 CenterHead 的候选来源网格提取实例特征，关联到二维占据 BEV 高度柱。
- 空间范围上，StreamOcc DQA 枚举框的三维轴对齐包围区域；当前方案进行 LiDAR—ego 坐标对齐后，按旋转框的 XY 投影建边：

| | StreamOcc 当前 DQA 实现 | 当前 DAOcc 改进 |
|---|---|---|
| 关联对象 | 三维体素 `(x,y,z)` | BEV 单元 `(x,y)`，代表一根高度柱 |
| 关联范围 | 旋转框外接的三维轴对齐包围区域 | 旋转框在 XY 平面的矩形范围 |
| 高度限制 | 限定枚举的高度范围 | 不单独区分高度层 |
| 朝向处理 | 旋转影响外接范围，但不逐点判断是否在旋转框内 | 将查询点旋转到框局部坐标系，判断是否在框内 |

- 融合方式上，StreamOcc 使用图跨注意力，当前方案采用内容、类别及几何编码生成消息，通过置信度加权聚合和门控残差更新 BEV，再由占据头预测各高度层类别。

3.1 候选优化：基于 3D 检测框的实例—占据 BEV 建边

当前 BoxBEVFusion 将实例分块，与全部占据 BEV 网格进行位置比较，仅对落在旋转框 XY 范围内的有效单元建立连接。该方式实现简单，但当目标覆盖区域较小时，会产生较多无效检查。

StreamOcc DQA 根据预测框角点确定局部网格范围，直接枚举包围区域内的体素，避免扫描全网格。两者区别如下：

| 项目 | StreamOcc DQA | 当前 `BoxBEVFusion` |
|---|---|---|
| 关联网格确定方式 | 根据框角点计算局部索引范围并枚举 | 分块比较实例与全部 BEV 网格 |
| 关联范围 | 三维轴对齐包围区域 | 旋转框的二维 XY 范围 |
| 旋转框内部判断 | 不进行精确判断 | 判断单元是否位于旋转框 XY 范围内 |
| Python 循环方式 | 逐实例循环 | 每 32 个实例分块循环 |
| 是否扫描全网格 | 否 | 是 |
